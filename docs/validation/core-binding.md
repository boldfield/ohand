# Rust-to-Swift Core Binding Contract

Status: Proven on simulator with BridgeProbe.

This document specifies the Rust-to-Swift FFI boundary established by P01 and used by production native services in M1.

## Architecture

The core binding consists of:

1. **Rust FFI layer** (`core/src/ffi/`) — C-compatible types and functions generated from Rust domain types
2. **Generated C headers** (`ios/OhAndCoreBridge/ohand_core.h`) — Auto-generated by cbindgen from Rust source
3. **Swift wrappers** (`ios/OhAndCoreBridge/OhAndCore.swift`) — Type-safe Swift APIs over the C boundary
4. **iOS framework** (`OhAndCoreBridge`) — Xcode framework target linking the Rust static library

The Rust core remains unaware of Swift/iOS; all marshalling happens at the FFI boundary.

## Type Conversions

### Capture

The `Capture` struct represents a source recording or note with context. Field semantics:

- `capture_id` (String): Unique stable identifier for idempotent replay
- `text` (Option<String>): Optional source text (captured or transcribed)
- `audio_reference` (Option<String>): Optional reference to stored audio file
- `capture_instant` (String): ISO 8601 timestamp of capture moment (e.g., "2024-01-01T12:30:45Z")
- `timezone_id` (String): IANA timezone ID (e.g., "America/New_York")
- `utc_offset_minutes` (i32): Current UTC offset in minutes; may differ from canonical timezone (e.g., -300 for EST)
- `locale` (String): Locale identifier (e.g., "en-US")
- `calendar` (String): Calendar system (e.g., "gregorian")
- `item_scope` (String): Privacy scope indicator ("personal", "work", "session")
- `route_id` (String): Processing destination identifier ("local", provider name, etc.)
- `entry_locked` (bool): Whether capture origin was from locked device
- `created_at` (String): ISO 8601 timestamp of insertion time (idempotency key)
- `session_topic` (Option<String>): User-correctable session identifier (e.g., "therapy", "review")

C representation `OhAndCapture` uses:
- `*const c_char` for required strings (non-null; caller must keep alive)
- `*mut c_char` returned from FFI (caller must free with `libc::free` or wrapper)
- `*const c_char` for optional strings (null if absent)
- `u8` for booleans (0 = false, 1 = true)

Swift wrapper `Capture` provides idiomatic Optional<String> and Bool.

### Error Handling

FFI functions that can fail:
- Return null/zero on failure and populate an `OhAndError*` output parameter
- Caller must check both return value and error pointer
- Error pointer must be freed with `ohand_error_free` to prevent leaks
- Error message is valid only until `ohand_error_free` is called

Example flow (C-level):
```c
OhAndError* err = NULL;
OhAndCapture* result = ohand_capture_new(..., &err);
if (result == NULL) {
    const char* msg = ohand_error_message(err);
    // Use msg before freeing
    ohand_error_free(err);
}
```

Swift wrappers throw exceptions on error, isolating C error handling.

## Memory Ownership

### Captured FFI Pointers

Rules for pointer lifetime:

1. **Input pointers** (`*const c_char` parameters): Caller owns, valid for call duration only. FFI copies/validates data; no retained references.

2. **Returned pointers** (`*mut T`): FFI owns allocation. Caller must free with appropriate destructor:
   - `OhAndCapture*` → `ohand_capture_free()`
   - `OhAndError*` → `ohand_error_free()`
   - String C pointers from FFI calls are owned by the returned struct and freed together

3. **String ownership in OhAndCapture**:
   - Returned from FFI, all string pointers are FFI-allocated
   - `ohand_capture_free()` deallocates all strings and the struct
   - Do not free individual string fields; only call `ohand_capture_free()`

### Memory Safety Invariants

- **Null pointer dereference**: All output parameters checked before dereferencing. Valid pointers returned only when error is null.
- **Use-after-free**: Caller must not access `OhAndCapture` after `ohand_capture_free()`. Swift wrappers own lifetime.
- **Double-free**: Each returned pointer has one designated free function. Calling twice is undefined behavior; FFI does not guard.
- **UTF-8 validity**: All C strings are validated UTF-8 on entry/exit. Invalid UTF-8 is rejected with an error.
- **String lifetime**: Strings copied/validated at call boundary; caller may release input buffers immediately after return.

## Cancellation and Lifetime

M1 design does not implement async cancellation at the FFI boundary. Jobs are queued and processed asynchronously by the native job runner; cancellation is handled at the logical job level, not the C call level.

Thread safety: FFI functions themselves are thread-safe (no shared mutable state accessed without synchronization). Database access is serialized by Rust core; concurrent native calls from Swift are safe.

## Unicode and Localization

The FFI boundary passes UTF-8 byte strings. No string normalization occurs at the boundary.

- Input validation: Non-UTF-8 input is rejected with error `"Invalid UTF-8: ..."`.
- Output encoding: All returned strings are valid UTF-8.
- Locale/timezone: Captured as metadata strings; actual interpretation happens in the Rust core (I02).
- Example: A capture with `locale="ja-JP"` and `text="こんにちは"` round-trips intact.

## Proven Capabilities

P01 validates:

1. **ASCII text round-trip**: "Hello, World!" → Capture → retrieve → "Hello, World!"
2. **Unicode preservation**: Multi-script text (Devanagari, CJK, emoji) and combining characters preserved
3. **Optional fields**: text/audio_reference/session_topic round-trip as null/nil/present
4. **Signed integer handling**: UTC offset from -720 to +840 minutes (UTC-12 to UTC+14) round-trips correctly
5. **Boolean flags**: entry_locked and all state flags preserved
6. **Validation**: Missing text AND audio_reference rejected with error; valid captures created
7. **Large input bounds**: 1 MB text validated; capture creation succeeds
8. **Error messages**: UTF-8 error text extracted and presented to Swift caller
9. **Memory safety**: No crashes on ownership errors; all test scenarios complete with proper cleanup

## Build Integration

iOS framework `OhAndCoreBridge`:
- Depends on: Rust static library (built as part of Xcode build, linked from prebuilt or artifact)
- Exports: Generated C header `ohand_core.h` + Swift module `OhAndCoreBridge`
- No public C APIs; all public exports are Swift types

Xcode build process:
1. Run Rust build if needed (managed by script phases or prebuild)
2. Link static Rust library into framework
3. Copy/generate C headers into framework public headers
4. Compile Swift wrappers
5. Link against C FFI boundary

Header generation:
- `core/build.rs` runs `cbindgen` to generate `ohand_core.h` from Rust source
- Output placed in `ios/OhAndCoreBridge/` for Xcode inclusion
- Regenerated on every Rust build; C declarations kept in sync automatically

## Limitations and Future Work

Not covered in M1:

- **Async/cancellation boundary**: FFI calls are synchronous; jobs/cancellation managed by queue layer above
- **Streaming/large results**: All results are in-memory; no streaming iterators across FFI
- **Callbacks from Rust**: Rust does not call back into Swift; all communication is request-reply
- **Raw binary data**: All boundary types are strings; audio/binary blobs are references, not raw bytes
- **Versioning**: No FFI versioning or negotiation; breaking changes require coordinated updates
