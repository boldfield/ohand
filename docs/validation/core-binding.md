# Rust-to-Swift boundary validation (P01)

P01 proves one small, real call boundary between the Rust core and Swift before product code commits to it. It is a probe, not the production bridge: B01/B01a own `core/src/ffi/`, `ios/OhAndCoreBridge/` and `tools/bindings/` and reuse what is established here. B01a made header generation reproducible build output and defined how modules declare exports (below).

## Decision

Hand-written `extern "C"` functions with a header generated by [cbindgen](https://github.com/mozilla/cbindgen), imported into Swift through a bridging header. A general RPC layer was rejected as out of scope; an object-model generator (UniFFI) was not needed to answer the questions below and adds a Swift-side generation step that the first bridge does not need. If B01 finds this surface too narrow, that is a B01 decision with this probe as its baseline.

## What exists

| Path | Role |
| --- | --- |
| `core/bindings/src/lib.rs` | The entire C ABI. |
| `core/bindings/src/probe.rs` | Boundary-independent logic: request parsing, size bound, cancellation checkpoints, calls into the real `ohand-core` capture store. |
| `tools/bindings/` | Build tooling in its own Cargo workspace: generates the C header with cbindgen and checks a built static library against it. The header is build output (`target/bindings-header/` for host checks, `$OHAND_RUST_OUTPUT_DIR` for Xcode) and is never committed. |
| `core/bindings/build-ios.sh` | Xcode run-script phase: builds `libohand_bindings.a` for the SDK and architectures being built and merges them with `lipo`. |
| `ios/BridgeProbe/Sources/Boundary/` | Swift wrapper (`OhandBoundary.swift`), bridging header and the launch self-check. |
| `ios/BridgeProbe/Tests/BoundaryTests.swift` | XCTest suite that calls the real Rust library; target `BridgeProbeTests`, run by the `OhAndTests` scheme. |

`core/bindings` is a workspace member (a one-line addition to the root `Cargo.toml` plus the resulting `Cargo.lock` entries) and the Xcode wiring is confined to the `BridgeProbe` and `BridgeProbeTests` targets in `ios/project.yml`. Both are shared files whose other editors (F02, F05) are ancestors of P01 in the dependency graph, so the edits are serialized; P01 cannot build or run on a simulator without them. B01a later edited these shared files again (see the ownership allowance in `docs/features/m1-task-refinement.md`).

## Reproducible bindings and module-local exports (B01a)

- `tools/bindings/generate.sh <dir>` writes `<dir>/ohand_bindings.h` from the `ohand-bindings` crate plus every `ohand-core` module (`tools/bindings/cbindgen.toml`: `parse_deps`, `include` and `extra_bindings` name `ohand-core`). It runs `cargo run --locked`, so the same sources and `Cargo.lock` give the same bytes; the generator tests compare repeated runs and the command-line tool's output.
- Xcode: `core/bindings/build-ios.sh` (the pre-build script of each target that links the core) generates the header into `$OHAND_RUST_OUTPUT_DIR` and builds the library there. Targets point `HEADER_SEARCH_PATHS` and `LIBRARY_SEARCH_PATHS` at that directory, so Swift and Rust consume the same generated file for the simulator and device slices.
- **Declaring an export (B01b, B01c and later).** Add a file under `core/src/ffi/` with `#[no_mangle] pub extern "C" fn ohand_...` functions and a `pub mod` line for it in `core/src/ffi/mod.rs`, which those tasks own. `core/bindings/src/lib.rs`, the generator and its configuration are not edited. The `ohand-bindings` crate already links `ohand-core`, so the symbol is in `libohand_bindings.a`, and the generator parses `ohand-core`, so the declaration is in the header. A module without the `pub mod` line is exported nowhere.
- **Naming.** Functions are `ohand_*` and constants `OHAND_*`. Public constants of `ohand-core` without that prefix are removed from the header (cbindgen otherwise exports every public constant of a binding source). Types appear only when an exported function uses them. A header function without the prefix fails the library check.
- **Target independence.** cbindgen does not evaluate target `cfg`, so the header is the same for every target. A test fails if the exporting sources (`core/bindings/src`, `core/src/ffi`) gate code on `cfg(target_...)`. `check-library` (`make check` on the host; `build-ios.sh` for each simulator and device slice of a Debug build, before `lipo`) compares `nm` output of the built `.a` with the header in both directions: a declared function that is not exported, or an `ohand_` export that is not declared, fails the build. Release libraries are LTO bitcode that `nm` cannot read, so Release is not inspected; it builds from the same sources and header.
- **Evidence.** `tools/bindings/tests/module_local_exports.rs` builds a throwaway workspace with the same layout (`ohand-core` with an `ffi` module, `ohand-bindings` staticlib), adds a function and a constant in a module under `ffi/` with no edit to the binding crate, and asserts that they reach the generated header and the built library, that unrelated core constants do not, and that an undeclared module reaches neither. The fixture lives in a temporary directory, so no test symbol is part of the shipped ABI. `make check` also generates the real header and runs the library check against the real `libohand_bindings.a`.
- **Round trip.** `BridgeProbe` and `BridgeProbeTests` import the generated header and call the real core through it on the simulator (`ios.yml`), which is the minimal value/error round trip; B01a adds no product operations.

## Core handle and callbacks (B01b)

`core/src/ffi/core_handle/` exports the safe native handle (`ohand_core_*`); `ios/OhAndCoreBridge/CoreHandle.swift` is its Swift wrapper.

- **Handles** are non-reusable `u64` registry keys, never pointers. Zero, stale, foreign and double-closed handles are rejected with the permanent `invalid_handle` failure; no export dereferences caller-supplied handle memory. `ohand_core_live_handles` and `ohand_core_live_result_buffers` expose leak counters.
- **Results** are `{status, data, len}` with Rust-allocated bytes released once by `ohand_core_result_free` (idempotent, null-safe). Failure payloads are the fixed content-free JSON `{class, code, message}` already used by the provider contracts; storage errors are classified by typed SQLite codes, never by message text. Panics become the `internal` failure and never cross the ABI.
- **Callbacks** run on the core's single worker thread (`ohand-core-worker`), one at a time, in submission order. Once `ohand_core_cancel`, `ohand_core_set_event_callback` or `ohand_core_close` returns, no callback is running or will start; the context can then be released. `cancel` is allowed from inside a callback; `close` and replacing the callback are rejected there as `reentrant_call`.
- **Swift** imports the generated header through the clang module `OhandCoreC` (`ios/OhAndCoreBridge/CoreC/`) because a framework cannot use a bridging header. A target that imports it needs that directory on `SWIFT_INCLUDE_PATHS` and the Rust output directory on `HEADER_SEARCH_PATHS`. `CoreHandle` hops events to the main queue and runs handlers only there. Once `cancel()`, `close()` or `setEventHandler` returns, the old handler never starts again. Called off the main queue, these calls wait for a handler invocation that has already been claimed, so it has finished or never starts. Called on the main queue (for example from a handler), they cannot wait for themselves, but no handler can be running concurrently there. Deadlock constraint: a handler must not synchronously wait on a thread that is cancelling, closing or replacing the handler of the same handle.
- The framework statically links the Rust library; `core/bindings/build-ios.sh` takes a lock so parallel Xcode targets do not race on rustup and the shared cargo target directory.

Evidence: the `ffi::core_handle` Rust tests (run by `make test`) drive the exports as Swift does, and `ios/Tests/CoreBridge/CoreHandleTests.swift` runs in `OhAndTests` against the real core on the simulator (macOS CI; see the pull request for the run).

## Contract demonstrated

- **Data**: requests and responses are UTF-8 JSON byte buffers with explicit lengths. NUL bytes inside text never truncate it, and no function depends on NUL termination. The capture-shaped value is validated by, and stored through, the real `ohand_core::store::captures` API in an in-memory database.
- **Normalized failures**: every call returns `OhandResult { status, data, len }`. Status 0 is success; 1-5 are the contract classes `transient`, `permanent`, `unauthorized`, `cancelled`, `unsupported` (the probe emits `permanent` and `cancelled`). The payload is JSON `{class, code, message}` with fixed messages that never echo caller content.
- **Bounds**: requests longer than `OHAND_MAX_REQUEST_BYTES` (1 MiB, counted in bytes) are rejected as `request_too_large` from the length alone, before any caller memory is read.
- **Ownership**: Rust allocates each result buffer; Swift copies the bytes and releases the buffer exactly once with `ohand_result_free`, which clears the struct so a second free is harmless. Stores and cancel tokens are opaque handles released with their `_free` function. Null is accepted by every release function. `ohand_bindings_live_allocations` counts live Rust-owned objects so tests can assert that every success, failure, cancelled and panic path returns the count to its baseline.
- **Lifetime**: the Swift `ProbeStore` wrapper takes a lock around every call and around `close()`, so a handle is never freed while Rust is using it; calls after `close()` fail with `store_closed`.
- **Cancellation**: calls are synchronous and cooperative. Cancellation is observed at three points: call entry, after validation, and immediately before the commit. A call that reports `cancelled` has changed nothing (the open transaction is dropped, which rolls it back). Once the commit has happened the call succeeds, and a late `cancel()` never undoes a committed capture. `cancel()` is safe from any thread and after the call finished. In-flight native work is not interrupted; that is the contract for effects that outlive their owner (cancelled work produces no mutation).
- **Panics**: every exported function that can run caller-influenced code converts panics into the `internal` failure instead of unwinding across `extern "C"`.
- **Unsafe surface**: functions that dereference caller pointers are `unsafe extern "C"` with documented safety requirements; null required arguments return `null_argument`.

## Evidence

Linux (`make check`, `make test`, run by `core.yml`):

- `core/bindings/tests/boundary.rs` drives the exported C functions exactly as Swift does: ASCII and Unicode round trip (combining marks, RTL controls, ZWJ emoji, interior NUL), idempotent retry, conflicting ID reuse keeping the original words, invalid UTF-8, malformed and unknown-field JSON, missing and mutually absent fields, null pointers, exact size bound (limit accepted, limit+1 rejected, multibyte counted in bytes, bogus pointer with oversized length never dereferenced), cancellation before the call, at each internal checkpoint (via the internal hook) and after completion, concurrent cancellation being all-or-nothing, live-allocation accounting, store isolation, and panic containment.
- `tools/bindings` tests (`make test`) and the header/library check (`make check`) are described above.

macOS (`.github/workflows/ios.yml`, simulator job):

- `xcodebuild test -scheme OhAndTests` builds `libohand_bindings.a` for the simulator through the run-script phase, links it into `BridgeProbeTests` and runs `BoundaryTests`, which repeat the Rust scenarios through the Swift wrapper plus Swift-specific ownership, lifetime-under-concurrency and thread-safety cases.
- `BridgeProbe` is then built and launched on the simulator. At launch it saves and reads back a Unicode capture through the real core and checks that invalid UTF-8 is rejected; a mismatch calls `fatalError`, so a broken boundary fails the smoke test, which requires the process to stay alive.

The run for the exact submitted commit, found with `gh run list --workflow ios.yml --commit <sha>`, is linked from the pull request together with the downloaded `ios-evidence` artifact (`OhAndTests.log` containing `** TEST SUCCEEDED **` and the `BoundaryTests` cases, and `smoke.log` ending with `Smoke test passed`). This document does not claim a result for any commit; the run is the evidence.

## Findings for B01

- A header generated by cbindgen with `language = C` is imported through a bridging header rather than a modulemap, which keeps the probe free of a framework or module-map target. The C symbols live in the app and test targets that link the static library. A module-based import was not evaluated.
- The Rust toolchain is pinned by `rust-toolchain.toml`; the iOS targets are installed by the run-script phase with `rustup target add`, and the Cargo build runs under `env -i` so Xcode's compiler variables do not leak into the bundled SQLite C build.
- The simulator slice needs `aarch64-apple-ios-sim` (and `x86_64-apple-ios` when Xcode builds an Intel simulator slice); there is no `x86_64-apple-ios-sim` Rust target.

## Not covered

- Physical device builds (`aarch64-apple-ios`) are scripted but not exercised here.
- Asynchronous Swift call styles and interrupting a call that is already running inside SQLite are not part of this probe.
